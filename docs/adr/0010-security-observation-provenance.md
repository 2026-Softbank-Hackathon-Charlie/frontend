# 0010. 보안 관측 상태와 판정 근거는 각 보고서의 실제 출처와 식별자로 연결한다

- 상태: 채택
- 날짜: 2026-11-08

## 상황

보안 화면은 발견 항목, 통제 평가, 취약점을 별도 API로 읽지만 발견 항목이 먼저 도착하면 아직 수집 중인 통제와 CVE까지 미연동으로 표시했다. 수집기가 연결되어 있어도 성공한 스캔이 없는 상태를 취약점 0건으로 읽을 여지가 있었다. 통제의 원인과 CVE 검사 출처는 상세 화면을 열어야 확인할 수 있었다.

## 결정

- 세 API의 수집 중·관측됨·미관측·수집 오류·미지원과 각 수집 시각을 구분한다. 새 조회 실패 시 보관된 결과는 마지막 성공 결과임을 표시한다. 수집 성공은 통제 통과로 바꾸지 않는다.
- 통제 정의는 controlId로, 실제 수집 출처는 environment와 source를 함께 맞춰 연결한다. API가 제공하지 않는 앱 소유 관계를 추정하지 않는다. 수집 코드와 별도 판정 구현이 있으면 각각 연결한다.
- CVE의 검사 메타데이터는 scanId와 digest가 모두 맞을 때 연결한다. 컨테이너의 scanId가 있으면 같은 검사 결과만 발생 위치로 연결하며, 구버전이 scanId를 생략하면 실제 digest 관계를 유지한다. 동일 advisory로 묶인 목록에서도 이미지별 검사 근거를 구분한다.
- 성공 스캔, 실제 CVE 또는 scanned 상태를 관측하지 못하면 미관측으로 남긴다. 선택 환경에 성공한 컨테이너 스캔이 없으면 다른 환경의 검사로 0건을 추정하지 않는다. API 원시 발생 건수와 고유 advisory·이미지·실행 관계의 집계는 구분한다.
- 각 행의 작은 근거 접기에 원본 reason, source, 검사 ID·digest·스캐너·검사 시각과 제공된 근거 URL을 넣는다. 구현 링크는 검토한 platform 31540bbe 커밋을 가리키며 실제 배포 버전의 증명은 아니다.
- 외부 링크는 실제 HTTP(S) 주소 중 userinfo 및 알려진 인증 query/fragment 키가 없는 것만 허용한다. 원본 API는 Authorization 헤더가 필요하므로 새 탭으로 직접 열지 않고 기존 인증된 OCSF 조회·내보내기 화면으로 연결한다. 관측하지 않은 HyperDX 검색 링크는 만들지 않는다.

## 검토한 대안

- 개요 조회 완료를 전체 완료로 취급: 서로 다른 API의 대기와 실패를 구분하지 못한다.
- scanner.connected만으로 0건 표시: 저장소 접근 가능과 성공한 이미지 검사를 혼동한다.
- CVE ID나 digest만으로 검사 메타데이터 연결: 같은 advisory의 다른 이미지·검사 결과가 섞일 수 있다.
- 토큰을 URL에 붙인 보고서 링크: 브라우저 기록과 외부 요청에 인증 정보를 노출한다.

## 결과

기존 운영 GET 3종의 HTTP 상태와 집계·배열 형태를 읽기 전용으로 확인했고 실제 응답이 있음을 확인했다. 회귀 테스트는 API 지연, 환경별 통제, 다른 scanId/digest, 미검사, 링크 안전성을 확인한다. 새로운 스캔이나 클러스터 변경을 실행하지 않는다. 실제 브라우저 검증과 개별 취약점 악용 가능성 검증은 수행하지 않았다.
